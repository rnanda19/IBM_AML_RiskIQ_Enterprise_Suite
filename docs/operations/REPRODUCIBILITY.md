# Reproducibility: Evaluation and Demo Workflow

Status: honest evidence snapshot as of 2026-10-12 (Improvement 3, production-readiness pass).
This document should be read the same way as `RESILIENCE_TEST_PLAN.md` in this same directory:
the real, current state of this platform's reproducibility evidence, not a certification.

## What "reproducible" means for this repository

This is a portfolio/research demonstration built on a real, synthetic, published dataset
(Kaggle's "IBM Transactions for Anti Money Laundering (AML)", `ealtman2019`), not a live
production system. "Reproducible" here means: a second person, cloning this exact repository
with no prior context, can install the documented dependencies, run the documented commands,
and get the same passing test suite and the same notebook outputs this repository's own docs
already report -- without needing undocumented steps, secret values, or access this repository
itself doesn't already grant.

## 1. Dependency pinning

`requirements.txt` is machine-generated by `pip-compile` from `requirements.in` and is fully
version-pinned (`==`) for every one of its 156 entries -- confirmed by direct inspection during
this pass: no bare package name, `>=`, or `~=` constraint exists anywhere in the file. This
means `pip install -r requirements.txt` resolves to exactly the same dependency versions on any
machine, at any time, independent of whatever is newest on PyPI the day someone runs it.

## 2. The documented install + test commands are the same commands CI runs

`README.md`'s "How to Run" section documents:
```bash
pip install -r requirements.txt
pip install -e .
pytest tests/ -v
```
`.github/workflows/ci.yml`'s `test` job runs the identical sequence
(`python -m pip install -r requirements.txt`, `python -m pip install -e .`,
`python -m pytest tests/ -v`) on a genuinely clean GitHub Actions runner, on every push and
every pull request, across a Python-version matrix. This is the strongest reproducibility
evidence this repository has: not a one-time manual check, but a continuously re-run,
truly-clean-environment execution of the exact documented commands. See `ci.yml` itself and
this repository's commit history / Actions runs for the real, continuous evidence.

## 3. What was verified directly in this pass, and what was not

**Verified directly:**
- `requirements.txt` pinning (direct file inspection -- see above).
- The full local test suite (422 tests as of this pass) passes against this repository's own
  existing `.venv`, built via this exact documented install sequence.
- No unseeded randomness exists in `tests/` -- every `np.random`/`RandomState` use found during
  a repository-wide scan is seeded; test outcomes do not depend on wall-clock time or
  unseeded entropy.
- `.env.example` was audited against every `AML_RISKIQ_*` environment variable actually read
  anywhere under `src/` (via a direct grep-based cross-check). This caught and fixed a real
  gap: 9 of 13 variables (all of the Case Management Service's DB-path and alert-dispatch
  settings, plus the project-root override) were used in code but undocumented in the example
  file. `.env.example` now documents all 13, and
  `tests/unit/test_env_example_completeness.py` makes this a permanent, automated regression
  guard rather than a one-time manual fix.

**Not re-verified directly in this pass (and why):**
- A literal from-scratch `git clone` into a brand-new directory followed by a from-scratch
  `pip install -r requirements.txt` was attempted in this session's sandboxed environment, but
  the mounted-folder filesystem used for local work to reach the repository proved
  unreliable for repeated git operations on a freshly-created clone (lock-file and
  permission errors unrelated to the repository's own content). The attempt was abandoned
  rather than reported as passing without having actually passed; the scratch clone was
  deleted. This is a limitation of the local review environment, not a known defect in the
  repository itself -- CI's continuous, genuinely-clean-runner execution (point 2 above) is the
  authoritative clean-checkout evidence in its place.
- Notebook outputs (model metrics, PSI reports, etc.) were not re-run end-to-end in this pass;
  per this repository's own standing execution-boundary rule (see `README.md`), notebooks are
  run by a human on their own machine, and all real numbers and charts in this repository's
  reports come from that reported run, not from an agent executing the pipeline.

## 4. Deterministic test fixtures

Every test file under `tests/` builds its own fixtures inline (synthetic pandas DataFrames,
numpy arrays, SQLite temp files via `tmp_path`, FastAPI `TestClient` instances) rather than
depending on an external service, a shared database, or wall-clock-dependent state. Where a
test needs pseudo-randomness (e.g. `tests/unit/test_drift_monitor.py`'s PSI-band tests), it
uses a seeded `numpy.random.RandomState` with the seed and the resulting expected value
recorded in a comment, so the same assertion holds on every run, on every machine.

## 5. Configuration examples

`.env.example` (see point 3) documents every environment variable this platform's services
read, each commented out with a safe placeholder or documented default -- never a real secret.
See `SECRETS_MANAGEMENT.md` for the full secrets-handling policy this complements.
